## 三、场景 1：并发下单「不超卖」（主场景）

**准备（1 分钟）**
1. 手工跑一次「1-登录」→ 确认 token 已自动写入集合变量（若脚本未生效，手动复制响应里的 token 贴入变量）
2. 手工跑一次「2-下单」→ 应返回 `code=200`（成功单，消耗 1 件库存）

**压测（约 1 分钟）**
3. 选中「2-下单」→ 打开**性能测试**（或在性能测试模块新建场景、添加该接口）
4. 配置建议：
   - 并发数：**30**
   - 持续时间：**20 秒**（或“运行 20s / 不限循环数”）
5. 开始运行，观察报告

**期望现象**
- 前 ~50 个成功请求返回 `code=200`
- 库存售罄后其余请求**快速**返回 `code=3002`（Redis 预扣闸门直接拒绝，不打数据库——可观察这些请求响应时间明显更短）
- **绝不出现**「成功下单数 > 剩余库存」

**跑完后**：把 ApiFox 报告里的 **总请求数 / 成功数 / 失败数 / 平均 RPS / 平均响应时间 / P95** 发给 AI（截图或数字），AI 做数据库级核验并整理压测报告。

## 四、场景 2：网关限流验证（可选，做完场景 1 再切）

当前网关是"放开档"（90 秒内 RPS 上限 10 万，不会限流）。要验证真实限流：
1. 告诉 AI → AI 把网关切回默认档（**QPS=3**）
2. 你对「2-下单」再跑一轮性能测试（并发 20 / 10 秒）
3. 期望：**RPS 稳定在 ~3**，其余请求返回 HTTP **429**（`请求过于频繁，请稍后重试`）

## 五、数据核验（跑完由 AI 执行）

核验清单（不超卖判据）：

```sql
-- ① 库存账目：无负数；扣除量 = 成功订单量
SELECT sku_id, available, locked, sold FROM shop_stock.t_stock WHERE sku_id=103;
-- 期望：available + locked + sold = 50（总量守恒），available >= 0

-- ② 成功订单数（按压测标记）
SELECT COUNT(*) FROM shop_order.t_order WHERE remark='压测-apifox';
-- 期望：<= 起始可用库存（50）；且 = ① 中的扣除量

-- ③ Redis 双侧一致
GET http://127.0.0.1:8083/internal/stock/redis/103
-- 期望：redisValue = dbAvailable；consistent = true

-- ④ 库存流水无异常（无负库存记录）
SELECT COUNT(*) FROM shop_stock.t_stock_log WHERE sku_id=103 AND after_available < 0;
-- 期望：0
```

**验收标准**：①~④ 全部满足 → 「双层防护不超卖」验证通过；若有任何一条不满足，即为超卖/账目错乱，需排查。
