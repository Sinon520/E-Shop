# E-Shop 技术亮点（面试弹药库）

> 每个亮点都是「真实问题 → 方案取舍 → 实测数据」的完整闭环，可独立讲 3~5 分钟。
> 全部功能已在本地完整实现并验证：证据 = 冒烟脚本输出 + 数据库核对 + 压测报告。

## 亮点 1：商品缓存治理 —— 穿透 / 击穿 / 雪崩三件套 + 一致性

**一句话**：商品详情缓存做了完整防护——布隆过滤器 + 空值缓存扛穿透、Redisson 互斥锁重建扛击穿、TTL 随机抖动 + 启动预热扛雪崩，写入侧用「删除 + 延迟双删」保一致性。

**关键实现**（`eshop-product` → `ProductCacheService` / `CacheEvictWorker`）：

| 问题 | 方案 | 细节 |
|---|---|---|
| 穿透 | 两层：布隆过滤器（`product:bloom:spu`）+ 空值标记缓存（`__NULL__`，TTL 120s） | 布隆说"不存在"一定为真（无假阴性）；假阳性由空值缓存兜底；**未预热时布隆自动降级放行**，避免误杀 |
| 击穿 | Redisson `tryLock` 互斥重建 + 双检 | 锁等待 500ms 拿不到锁的线程**降级直查 DB、不回填缓存**（防惊群写放大） |
| 雪崩 | TTL 随机抖动（1800s + 0~300s）+ 启动异步预热 | 同批写入的 key 不再同时过期；预热即"以 DB 为准全量重建" |
| 一致性 | Cache Aside + 延迟双删 | 更新后：删缓存 → 延迟 2s 再删一次（**ZSET 自实现延迟队列**，成员=key、score=执行时间戳，200ms 轮询 + ZPOPMIN 原子取出） |

**取舍（面试加分点）**：
- 为什么不用 Redisson 的 `RDelayedQueue`？——3.52 版本已废弃（启动直接刷 ERROR），官方替代品 `RReliableQueue` 是 **PRO 授权功能**；改用 ZSET 自研，无授权依赖、重启不丢（数据在 Redis）、重复投递自动合并（同 key 覆盖 score）；
- 分类列表缓存不上互斥锁（重建成本低、并发重建无害）；商品**列表分页刻意不缓存**（筛选/排序/分页组合爆炸、命中率低，DB 索引足够）。

**证据**：`scripts/smoke-test-cache.ps1` 18/18 全过（含空值缓存命中、布隆拦截、延迟双删全链路）；缓存状态可视化接口 `/internal/cache/spu/{id}`。

**追问预案**：
- *"布隆过滤器里的商品下架了怎么办？"* → 布隆只增不减，删除无法撤销位；我们的兜底是"布隆放行后查库为空 → 写空值缓存"，穿透由第二层拦住；
- *"延迟双删为什么是 500ms/2s？"* → 目的是覆盖"更新期间并发读把旧值回填缓存"的窗口期，取值略大于一次主从复制/查询耗时即可。

## 亮点 2：RocketMQ 延迟消息——订单超时自动关单

**一句话**：下单成功后发送 30 分钟延迟消息；到期仍未支付则自动关单并回补库存，已支付/已取消的订单收到消息幂等跳过。

**关键实现**（`eshop-order` → `OrderTimeoutProducer` / `OrderTimeoutConsumer` / `OrderService#handleTimeout`）：
- 延迟级别可配（`eshop.mq.order-timeout-delay-level`，默认 16 = 30 分钟；本地演示用 3 = 10 秒）；
- 消费逻辑：查订单状态 → 仍待支付则 **CAS 0→5（超时关闭）** + 回补库存；非待支付 → 静默跳过；
- **可靠性设计**：发送失败不阻断下单（日志留痕，订单仍可支付/取消）；消费端系统异常抛给 RocketMQ 自动重试（重试进入后先查状态，天然幂等）；回补库存按 `(order_no, sku_id, type)` 流水幂等。

**为什么不扫表定时任务**：消息驱动更实时（精确到毫秒级触发），且天然分布式（多实例消费不重复）；扫表方案有延迟粗、全表扫描压力两个硬伤。

**证据**：`scripts/smoke-test-mq.ps1` 11/11——含三场景：超时自动关闭+回补 ✅ / 已支付订单不被误关 ✅ / 已取消订单幂等跳过 ✅；延迟精度实测 10.05 秒（10 秒档）。

## 亮点 3：分布式事务双路线——Seata AT + MQ 最终一致

**一句话**：强一致场景（下单 = 创建订单 + 锁库存）用 Seata AT 全局事务收敛；异步场景（支付回调、超时关单）走 MQ + 幂等最终一致——两条路线都真实落地，各自 trade-off 能讲清。

**关键实现**：
- Seata Server 2.5.0（**db 存储模式**，事务状态持久化；客户端与 TC 通过 Nacos 发现）；
- 下单接口 `@GlobalTransactional`：order 库（订单/明细/日志）与 stock 库（库存/流水）两个分支同一全局事务，**任一步失败整体回滚**；
- **Feign XID 传播**：拆包发现 SCA 的 seata starter 只带"HTTP 服务端恢复 XID"的集成、**没有 Feign 客户端集成**——自补 10 行 `RequestInterceptor`（`RootContext.getXID()` → `TX_XID` 请求头），下游自动加入全局事务；
- 回滚证据：`branch register`（双服务分支注册 + 全局锁）→ `Branch Rollbacking` → `undo_log deleted` → `PhaseTwo_Rollbacked`。

**取舍（面试必讲）**：
- **AT vs MQ 最终一致怎么选**：下单主链路要"用户体验即时反馈 + 数据强一致"→ AT（两阶段但业务无感）；支付回调/超时关单是"可异步、可重试"→ MQ 最终一致（解耦 + 天然幂等重试）；
- 改造后的行为升级：库存不足从 P1 的"创建订单后自动取消（有残留）"变为 **全局回滚（数据库零残留）**。

**证据**：库存不足下单 → 返回 3002 且订单表**零残留**；正常单可观测到同一 XID 下两个服务各自分支 + 全局锁（`lockKeys: t_order, t_order_item, t_order_log / t_stock, t_stock_log`）。

## 亮点 4：双层防超卖——Redis Lua 预扣 + DB 乐观锁

**一句话**：抢购场景的并发入口用 Redis Lua 脚本原子预扣（快、拦截率 96%），最终账本用 DB 乐观锁（数学上不可能超卖），两层各司其职。

**关键实现**（`eshop-stock` → `StockRedisGate` + `lua/stock_deduct.lua`）：
- **第一层（闸门）**：Lua 单线程内完成"判断余量 + DECRBY"——三态返回（成功 / 余量不足直接拒绝 / 无缓存降级放行）；**Redis 是加速层而非依赖层**，任何异常自动降级放行由 DB 兜底；
- **第二层（账本）**：`UPDATE ... SET available = available - n, version = version + 1 WHERE sku_id = ? AND version = ? AND available >= n`，冲突重试 3 次；
- 一致性闭环：下单失败补偿回滚已预扣的 Redis；取消/超时回补时 Redis 同步加回（幂等由流水去重保证）；**预热 = 以 DB 为准全量重建**（重启自动对账，收敛漂移）。
- 加回脚本有个细节：**仅当 key 存在才 INCRBY**（不给未预热的 SKU 凭空造值）。

**取舍**：Redis 与 DB 允许短暂漂移（如 Seata 回滚不经过 stock 服务时）——漂移方向恒为"偏严格"（少卖不超卖），且由预热/校准收敛。这是我们主动选择的可用性 > 强一致的边界。

**证据**：`scripts/smoke-test-stock-lua.ps1` 10/10（下单双侧同步 -1、不足 Lua 层拦截未扣减、取消双侧回补）；**压测：1215 并发请求恰好成交 50 单 = 库存量，零超卖**。

## 亮点 5：网关层——Sentinel 限流 + Feign 熔断降级

**一句话**：网关对下单接口做 QPS 限流（统一 429 JSON 响应）；订单服务对"订单→库存"的 Feign 调用配置异常比例熔断，下游故障时快速失败并统一降级文案。

**关键实现**：
- 网关（`SentinelGatewayConfig`）：自定义 API 分组精确匹配 `/api/order/create` + `GatewayFlowRule`；阈值可配置（演示档 3 / 压测档放开）；限流响应与全站统一 JSON 同构；
- 熔断（`SentinelDegradeConfig` + `StockClientFallbackFactory`）：异常比例规则（10s 窗口 ≥5 次且异常 >50% → 熔断 10s）；**Feign 资源名格式 = `HTTP方法:目标URL:路径`**（从字节码解出：`POST:http://eshop-stock/internal/stock/lock`）；
- 认知点：`fallbackFactory` 对**调用异常**同样生效（不只熔断）——下游实例摘除后第一次调用就会走降级。

**证据**：8 并发真请求 → 恰好 3 过 5 限；停掉库存服务 → 前 2 次异常降级、第 3 次起熔断拦截（block 日志 `DegradeException`）、恢复后 10 秒自动闭合；**限流压测：40419 次洪峰 99.85% 拦截，放行精确 60 个**。

## 亮点 6：压测数据（最硬的面试素材）

| 场景 | 参数 | 结果 |
|---|---|---|
| **不超卖** | 30 并发 × 20s，打 50 件库存 | 总 1215 请求 → **成交 50（= 库存，零超卖）**；拒绝 1165 全由 Redis 闸门拦截；**0 失败**；RPS 60.2 |
| **限流** | 30 并发 × 20s，网关 QPS=3 | 尝试 40419 次 → **429 拦截 99.85%**；放行精确 60（= 3×20s）；429 仅 **14.6ms**（业务链路 1/11 成本） |

**三层防护成本梯度**（同一接口的响应耗时）：限流 429（14.6ms）→ 库存拒绝（485ms）→ 成功下单（702ms）——**越靠前的拦截越便宜，"把无效流量挡在最外层"的价值被量化**。Little's Law 验证：30 并发 ÷ 0.494s ≈ 60.7 RPS ≈ 实测 60.2。

证据：`docs/pressure-test-report.md`（完整报告）+ 数据库核验 6 项（库存守恒 / 订单数 / 负库存 0 / 双侧一致）+ 复现脚本 `scripts/pressure-test.mjs`。
