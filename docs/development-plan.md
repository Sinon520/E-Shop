## 一、项目定位与目标

**一句话**：一个覆盖「浏览 → 加购 → 下单 → 支付 → 履约」完整闭环的 B2C 自营商城，以微服务架构承载真实的高并发场景。

三个目标（按优先级）：

1. **全链路可用**——线上能演示，不是只能跑本地的 demo
2. **每个技术决策能讲清**——为什么拆服务、为什么要 Seata、不加会怎样
3. **工程完整度**——代码结构、接口文档、部署脚本、压测报告齐全

### 2.2 服务清单（7 个运行单元）

| 服务 | 端口 | 职责 |
|---|---|---|
| eshop-gateway | 9000 | 统一入口：路由、JWT 鉴权、网关限流、跨域 |
| eshop-user | 8081 | 注册 / 登录 / 用户资料 / 收货地址 |
| eshop-product | 8082 | 分类 / SPU / SKU / 商品详情 / 上下架 / 商品缓存 |
| eshop-stock | 8083 | 库存查询 / 预扣 / 确认扣减 / 回补 |
| eshop-cart | 8084 | 购物车（Redis Hash，不进 MySQL） |
| eshop-order | 8085 | 下单 / 订单状态机 / 列表详情 / 超时关单 |
| eshop-pay | 8086 | 支付单 / 模拟支付 / 回调（幂等） |
| eshop-common | — | 公共依赖库：统一响应、全局异常、JWT 工具、常量、DTO |

**拆分粒度取舍**：
- 建议保持 7 个运行单元——库存独立，「订单-库存」才有分布式事务的戏份；购物车独立符合服务边界，顺带展示 Redis 实战。
- 若想压缩工作量：cart 可并入 order、stock 可并入 product（缩为 5 个单元），代价是分布式事务场景与边界设计亮点变弱。
- 不建议再细拆（如独立 auth / 搜索服务），个人项目维护成本会失控。

## 四、核心流程设计

### 4.1 下单主链路（核心中的核心）

```
① 用户提交订单（购物车勾选 / 立即购买）
② [订单服务] 校验商品状态与价格 → 创建订单（待支付）
③ [订单服务] → [库存服务] 锁定库存      ← Seata AT 全局事务
④ 返回订单号 → 跳转模拟收银台
⑤ [支付服务] 创建支付单 → 模拟支付成功
⑥ [支付服务] 回调处理（幂等：唯一索引 + 状态机）
⑦ [订单服务] 状态 → 已支付；[库存服务] 确认扣减（可用 → 已售）
⑧ 订单完成（管理后台发货 → 确认收货）
```

**异常兜底**：
- ③ 任一步失败 → Seata 全局回滚，订单置为已取消
- ⑤~⑦ 用户迟迟不支付 → RocketMQ 延迟消息 30 分钟后触发：仍未支付则关单 + 回补库存（幂等）

### 4.2 防超卖（双层防护）

1. **Lua 原子预扣**：Redis 中用 Lua 脚本原子判断并扣减——抗并发入口
2. **乐观锁兜底**：DB 层 `UPDATE ... SET available = available - N, version = version + 1 WHERE sku_id = ? AND available >= N AND version = ?`——保证最终正确性
3. 用 JMeter 做并发下单压测，**用数据证明不超卖**——这份报告就是面试素材

### 4.3 订单超时关闭

- RocketMQ 延迟消息（30 分钟级别）
- 消费者：查订单状态 → 未支付则关单 + 回补库存（幂等处理）
- 为什么不用定时任务扫表：消息驱动更实时，且能讲清「延迟消息」原理

### 4.4 缓存设计（商品域）

| 问题 | 方案 |
|---|---|
| 穿透 | 布隆过滤器（商品 ID）+ 空值缓存 |
| 击穿 | 互斥锁重建（Redisson）/ 逻辑过期 |
| 雪崩 | TTL 加随机偏移 + 缓存预热 |
| 一致性 | Cache Aside：先更库、再删缓存 + 延迟双删兜底 |
| 热点（可选） | Caffeine 本地缓存 + Redis 两级 |

### 4.5 分布式事务选型（双路线落地）

| 场景 | 方案 | 理由 |
|---|---|---|
| 下单 = 创建订单 + 锁定库存 | **Seata AT** | 强一致诉求、接入成本低、面试高频 |
| 支付回调 → 订单/库存更新 | **MQ + 幂等** | 异步化、可重试、最终一致 |
| 超时关单 → 回补库存 | **MQ 延迟消息 + 幂等** | 同上 |

两条路线都会真实落地（强一致 vs 最终一致），能讲清各自 trade-off，比只用一个更有说服力。

### 4.6 认证与鉴权

- **登录**：用户服务签发 JWT（access 2h + refresh 7d，refresh 白名单存 Redis）
- **网关**：统一校验 JWT → 解析用户 ID 写入内部请求头（X-User-Id）→ 下游服务信任内网
- **管理后台**：独立账号体系（admin 角色），网关按路径前缀区分鉴权策略

## 五、数据库规划（按服务分库）

| 数据库 | 归属服务 | 核心表 |
|---|---|---|
| shop_user | 用户 | t_user、t_user_address |
| shop_product | 商品 | t_category、t_brand、t_spu、t_sku |
| shop_stock | 库存 | t_stock、t_stock_log |
| shop_order | 订单 | t_order、t_order_item、t_order_log |
| shop_pay | 支付 | t_payment、t_pay_callback_log |
| —（Redis） | 购物车 | cart:{userId}（Hash 结构） |

**设计原则**：
- 禁止跨库 JOIN，跨域数据靠服务调用或冗余字段
- 订单表冗余商品快照（名称 / 单价 / 图片），不依赖商品服务实时查询
- 金额统一 DECIMAL(10,2)；全表带 create_time / update_time + 逻辑删除
- 详细 DDL + E-R 图在 Phase 0 交付

## 八、技术亮点清单（面试弹药库）

1. **服务拆分**：7 个单元如何定边界，为什么库存要独立
2. **分布式事务双路线**：Seata AT（强一致）vs MQ 最终一致，各自适用场景
3. **防超卖**：Redis Lua 预扣 + DB 乐观锁双层防护 + 压测数据
4. **消息驱动**：RocketMQ 延迟消息关单、回调幂等（唯一索引 + 状态机）
5. **缓存治理**：穿透/击穿/雪崩三件套 + Cache Aside + 延迟双删
6. **网关层**：JWT 统一鉴权 + Sentinel 限流 + 内部身份透传
7. **商品搜索**：ES + IK 分词，倒排索引与相关性排序（P4 落地）
8. **工程化**：Knife4j 接口文档、Docker Compose 一键起栈、JMeter 压测报告
