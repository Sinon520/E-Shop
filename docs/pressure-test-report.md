# E-Shop P2 压测报告：不超卖与网关限流

> 日期：2026-10-14 ｜ 版本：1.0.0-SNAPSHOT ｜ 工具：自研 Node.js 并发压测脚本（`scripts/pressure-test.mjs`，固定并发模式）
> **一句话结论：1215 个并发下单请求，恰好成交 50 单（= 库存总量），零超卖；4 万次限流洪峰，99.85% 被网关拦截，后端零失败。**

---

## 一、测试目标

1. **证明不超卖**：在远大于库存的并发压力下（30 并发打 50 件库存），成交数必须 ≤ 库存数，且库存账目守恒、无负库存；
2. **证明限流生效**：网关 Sentinel 限流阈值 QPS=3 下，多余流量被快速拒绝（HTTP 429），放行速率精确可控。

## 二、测试环境

| 项 | 说明 |
|---|---|
| 架构 | 完整 7 微服务链路（gateway → order → product/stock/user/cart，含 Seata 全局事务、RocketMQ、Redis） |
| 部署 | 本机单机混部（7 服务 + MySQL/Redis/RocketMQ/Nacos/Seata/Sentinel 同机） |
| 目标接口 | `POST /api/order/create`（经网关全链路，含 JWT 鉴权） |
| 压测目标 SKU | sku103，库存基线重置为 **50 件**（Redis 预扣值同步 50/50） |
| 防护机制 | Redis Lua 原子预扣（第一层闸门）+ DB 乐观锁（第二层账本） |
| 其他 | 订单超时关单为 30 分钟档（确保压测窗口内不发生超时回补，账目干净） |

## 三、场景 1：高并发下单「不超卖」

### 3.1 参数

并发 30 ｜ 持续 20 秒 ｜ 每请求购买 1 件 ｜ 无思考时间（最大化压力）

### 3.2 压测数据

| 指标 | 数值 |
|---|---|
| 总请求数 | **1215** |
| 成功下单（code=200） | **50** |
| 库存不足拒绝（code=3002） | 1165 |
| HTTP 失败 / 网络异常 | **0 / 0** |
| 平均 RPS | 60.2 |
| 响应时间 平均 / P50 / P95 / P99 / Max | 494 / 423 / 977 / 1177 / 1522 ms |
| 成功单 平均 / P95 | 702 / 1127 ms |
| 拒绝单 平均 / P95 | 485 / 961 ms |

### 3.3 数据核验（核心）

| # | 核验项 | 结果 | 判定 |
|---|---|---|---|
| ① | 库存账目：available / locked / sold / 总量 | 0 / 50 / 0 / **50** | ✅ 总量守恒 |
| ② | 成功订单数（remark=压测-node） | **50** | ✅ = 库存量 |
| ③ | 订单明细行数 | 50 | ✅ 一一对应 |
| ④ | 库存流水新增 lock 记录 | 50（总计 52 = 50 + 2 笔历史单） | ✅ |
| ⑤ | 负库存流水（after_available < 0） | **0** | ✅ 无超标扣减 |
| ⑥ | Redis 双侧一致 | redisValue=0 = dbAvailable=0 | ✅ |

### 3.4 结论

**1215 个并发请求中恰好 50 个成交，与库存总量严格相等——零超卖。** 其余 1165 个请求被"Redis Lua 预扣闸门"直接拒绝（拒绝路径未穿透到数据库层，日志中 `Redis 预扣拒绝` 逐条可查），DB 乐观锁作为最终账本全程兜底（无任何负库存记录）。请求洪峰下系统零失败（无 HTTP 5xx、无网络异常）。

## 四、场景 2：网关限流

### 4.1 参数

并发 30 ｜ 持续 20 秒 ｜ 网关 Sentinel 限流档 **QPS=3**（生产演示档）｜ 库存已售罄（放行的请求将得到 3002）

### 4.2 压测数据

| 指标 | 数值 |
|---|---|
| 总请求尝试 | **40419** |
| 限流拒绝（HTTP 429） | **40359（99.85%）** |
| 放行进业务（code=3002，库存不足） | **60**（= 3 QPS × 20 秒，精确吻合） |
| HTTP 失败 / 网络异常 | **0 / 0** |
| 请求尝试速率 | 2020 次/秒 |
| 429 响应时间 平均 / P95 | **14.6 / 25.8 ms** |
| 放行请求响应时间 平均 / P95 | 162.6 / 288.4 ms |

辅助证据：Sentinel 本地拦截日志（`sentinel-block.log`）逐秒记录，峰值每秒拦截 **2520** 次；限流响应为统一 JSON（`{"code":429,"message":"请求过于频繁，请稍后重试"}`）。

### 4.3 分析

1. **放行精度**：20 秒内恰好放行 60 个请求（3/秒 × 20 秒），限流器精度达个位级；
2. **拦截效率**：99.85% 的洪峰流量在网关最外层被拒绝，**拦截耗时（14.6ms）仅为业务链路耗时（162.6ms）的 1/11**——限流层用极低成本保护了后端全部服务；
3. **零穿透事故**：4 万次请求下后端零失败、零异常；
4. 注：请求尝试速率（2020/s）反映的是"被拒后客户端持续重试"的压测工具行为；**进入业务系统的有效速率被严格限制在 3 QPS**。

## 五、分析与讨论

1. **排队模型验证（Little's Law）**：L = 30 并发，W ≈ 494ms → 预期吞吐 λ = L/W ≈ 60.7 RPS，实测 60.2 RPS，模型高度吻合；
2. **双层防护的成本梯度**（响应耗时对比）：成功单（702ms，含全局事务提交 + MQ + 清购物车）> 拒绝单（485ms，Redis 闸门截断）> 限流 429（14.6ms，网关层拒绝）——**越靠前的拦截越便宜**，这正是"多层防护"的意义；
3. **瓶颈观察与优化建议**（后续可做）：
   - 拒绝路径仍经过"地址校验 + 商品快照"两次远程调用后才到库存闸门——可将**库存预检前移至订单校验阶段**（或网关侧熔断缓存），进一步降低无效损耗；
   - 成功单 P95 达 1.1s：地址查询与 SKU 快照为串行 Feign 调用，可并行化；
   - 本机单机混部下所有服务争抢 CPU/内存，生产多节点部署指标会显著提升；
4. **测试工具说明**：本次使用自研 Node.js 脚本（无第三方依赖、固定并发 + 无思考时间模式），指标口径与 JMeter / ApiFox 性能测试一致；ApiFox 侧亦已完成完整链路手工验证（登录 + 下单）。脚本与结果：`scripts/pressure-test.mjs`、`scripts/pressure-result.json`。

## 六、结论汇总

| 目标 | 结论 | 关键数据 |
|---|---|---|
| **不超卖** | ✅ 通过 | 1215 并发 → 恰好 50 成交（= 库存 50）；账目守恒、0 负库存、0 失败 |
| **限流生效** | ✅ 通过 | 40419 洪峰 → 99.85% 拦截；放行速率精确 3 QPS；429 响应 14.6ms |

> 面试讲解要点：①"不超卖"由**两层防护**保证——Redis Lua 原子预扣扛并发（拒绝 96% 的重复请求）、DB 乐观锁守账本（数学上不可能为负）；②"限流"验证了**多层拦截的成本梯度**（14.6ms → 485ms → 702ms），网关层用 1/11 的成本挡掉了 99.85% 的无效流量。
